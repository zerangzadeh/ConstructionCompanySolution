# CEP-011 — proposed DMS access decision

**Decision status:** APPROVED by the Human Decision Maker for CEP-011/IMB-0095 Development execution on local `main` on 2026-10-15. The approval overrides Migration Impact to SCHEMA for the three category fields and WorkRelationship typed link only; it does not authorize a data migration, production rollout, or CEP-013.

## Source and repository grounding

- `SPEC-017` requires employee-visible category policy for owner, sensitivity, current/history visibility, download, source link, version/supersession, and acknowledgement only if explicitly approved. It gives no category values. `PD-023` limits V1 to core DMS; `PD-029` leaves source authority in Workforce/DMS. ESS-CAP-014/016/018 require own source-linked records and download reauthorization.
- `DocumentCategory` is expressly descriptive and has no access fields. `Document.category` is nullable. `Document.current_version` and immutable `DocumentVersion` already distinguish versions. Existing DMS services require `DOCUMENTS_VIEW` or `DOCUMENTS_DOWNLOAD`, validate every typed link, deny unlinked/expired/sealed documents, and reauthorize the requested version. The template's download link visibility is not a backend grant.
- `Person` is the stable tenant identity with optional `User`; `WorkRelationship` is the effective-dated episode and may explicitly reference a legacy `Employee`. `Employee.user` is optional. The closed DMS link registry has qualification/training/performance source links but no Person or WorkRelationship link. Legacy Employee mapping is not automatically backfilled and may be absent or ambiguous.
- Existing generic DMS access and source-domain administration must remain authoritative. A new employee-facing path must apply the policy below at list, detail, version and download service boundaries; a UI filter alone is insufficient.

## Recommended bounded access contract

1. **Category policy.** For employee self-access, add three explicit deny-by-default controls to `DocumentCategory`: `employee_current_visible`, `employee_history_visible`, and `employee_download_allowed`. `employee_history_visible` governs prior `DocumentVersion` objects; an ended employment episode is governed separately below. A null, archived, or unconfigured category grants no employee self-access. Current policy is evaluated on each request so revocation takes effect; changes require existing tenant authorization and audit. These fields do not create access for generic/project DMS users. `Document.confidentiality`, scanner availability, expiry, archive, sealed evidence, and existing source checks remain additional denials. Do not derive policy from category code/name or template display.
2. **Subject and source.** Workforce owns the employee subject and employment episode; DMS owns the bytes and versions. For employment contract/personnel-order and other episode-owned documents, add one immutable, tenant-validated `WorkRelationshipDocumentLink` in Workforce, registered with the closed DMS link registry. The linked `WorkRelationship.person` is the subject. Do not add a generic `PersonDocumentLink` or `EmployeeDocumentLink` in this slice. Existing qualification/training evidence keeps its own source-record typed link; its `Employee` may resolve to a Person only through an explicit, unique `WorkRelationship.legacy_employee` mapping. Missing/conflicting mapping denies self-access. Person-level documents without an episode-owned source remain unavailable for employee self-service until separately decided.
3. **Authorization.** Every request requires active User, active tenant and membership, `DOCUMENTS_VIEW` for metadata/current/history, and `DOCUMENTS_DOWNLOAD` separately for bytes. Resolve the actor's `Person` by the explicit same-tenant `Person.user` link, never by name/email/employee number. Require an effective current `WorkRelationship` for employee self-service. A document qualifies only when all of its linked source objects are permitted: the WorkRelationship link belongs to that Person; qualification/training links resolve through the explicit legacy mapping; project/site links retain the existing project/site permission and object scope. A project document does not become employee-visible merely because the employee works on the project, and an employee link does not bypass a project restriction. Generic DMS administration continues under its existing source permissions; this decision grants no manager access by title or cross-employee self-access.
4. **Ended episodes and history.** Ending a WorkRelationship preserves its document/version links. While the actor has an active membership and an effective current WorkRelationship for the **same Person**, documents linked to that Person's ended episode may be viewed only when the category allows employee history. With no current WorkRelationship, self-service access ends; retention/export by authorized administrators remains separate. A rehire does not transfer documents to the new episode. No date, name, or legacy Employee similarity may establish ownership.
5. **Download and acknowledgement.** A visible document is not automatically downloadable. Require category download permission, `DOCUMENTS_DOWNLOAD`, the same subject/source checks, the permitted version class, and existing scanner/retention/access checks at the download backend. Acknowledgement is **not approved in this V1 slice**: no acknowledgement action, state, or implied evidence. It is neither optional descriptive metadata nor a mandatory lifecycle step. Any later acknowledgement feature requires a separate Product Decision and durable actor/time/document-version evidence; category configuration alone cannot create such a lifecycle.
6. **Disclosure and rollout.** List filtering and direct detail/version/download URLs must share the same decision and return a non-disclosing denial for cross-employee, unlinked, unmapped, expired, and out-of-scope objects. Existing documents/categories receive no inferred self-access. An authorized administrator may explicitly classify a category and link a source document after the schema is available. No automatic legacy backfill or advanced EDMS behavior is included.

## Minimal implementation boundary for Human decision

**Migration required: YES. Recommended Migration Impact: SCHEMA.** The minimum schema is three deny-by-default `DocumentCategory` policy fields and one Workforce `WorkRelationshipDocumentLink` table, with tenant/document/relationship foreign keys and an organization-scoped uniqueness constraint following existing typed-link conventions. Register that link in DMS and enforce it in services. No `Person`, `Employee`, `WorkRelationship`, `Document`, or `DocumentVersion` column change is required. No data migration is recommended: there are no approved per-category values or trustworthy legacy document-to-episode mappings to backfill. Existing categories default to no employee self-access; existing generic DMS access is preserved. Any requirement to expose historical legacy documents automatically would require separate mapping evidence and a separately authorized data-migration decision.

The Human Decision Maker approved the bounded override from canonical **Migration Impact = NONE** to **SCHEMA**. AC text and scoped DoD are unchanged. The Development implementation and validation are recorded in the CEP-011 completion report; production migration and rollout remain unauthorized.

## Approved bounded Human Decision

Override CEP-011 Migration Impact from NONE to SCHEMA solely for the three DocumentCategory fields and WorkRelationshipDocumentLink table.
