# B11 evidence replay

These scripts are validation sources, not application commands or production setup. Keep original evidence immutable. Write a fresh replay into a separately named evidence directory before running it. The published source hashes identify the required dirty source baseline, including incoming B03–B10 work.

1. Copy the replay Python files to the repository's `.scratch/b11-validation` directory in an independent checkout matching the intended source hashes. The scripts' relative paths require that location. Do not execute `bootstrap.py` from this evidence directory. Do not overwrite the completed session's private runtime, cluster or evidence.
2. Copy the two tiny synthetic PDFs in `assets` to `.scratch/b09-validation/assets`. Their existing B09 hash/scanner provenance is referenced by `b09_seed.py`. This is qualified fixture provenance and does not certify an external scanner integration.
3. Confirm PostgreSQL binaries, Python environment and the locally installed Playwright module directory. The recorded paths are Windows-specific. `bootstrap.py` initializes a new loopback private cluster, generates a private secret and migrates an empty B11 baseline. It asserts 302 matrix rows and clones original/retest databases. It must never target an existing environment database.
4. Load the generated private `env.ps1`, select `B11_DB=b11_original` or `b11_retest`, then run `sweep.py`. Fixture groups are transactional. The completed execution's intermediate missing field fixtures were recovered using `supplement.py` and explicit reviewer assignments. Extra role actors require effective `MembershipRoleAssignment` and scope grants, not legacy role strings. In the recorded execution, the catalog actor received the existing explicit `tenant_admin` role. My Requests uses an explicit Employee.user identity link and the manager is an explicit team lead.
5. `portal.py before/after`, label scripts, `exact_regression.py`, `journeys.py` and the state-view scripts record bounded current observations. State scripts create synthetic records and are not universally repeatable on an already seeded database. Use a fresh cloned B11 database, retaining original and retest outputs separately. The original and retest fixture manifests contain session-local identifiers and remain private rather than being published as reusable identity authority.
6. The document positive-detail recovery registers synthetic evidence through the existing domain registration service and selects `references(source)` for the exact pinned version. The field operation key is a UUID. A denied unpinned source/version is correct behavior, not proof of a missing page. `sweep.py` contains the final version-selection correction.
7. `journeys.py` accepts `B11_JOURNEYS` to select a case and `B11_JOURNEY_OUTPUT` for a separate artifact. The recorded successful final pointer uses the visible business document title/number, a pointer selection in the enhanced dropdown and the canonical source fragment. Earlier locator failures are retained in the evidence files. Do not treat an arbitrary raw reference query or a missing fragment expectation as a product defect.
8. Run focused Python checks only on private `test_b11_*` databases. See `regression-results.json` for the actual run outcomes and unresolved failure seams. Do not claim a green suite by excluding its disclosed failures.
9. Run `bootstrap.py final` only in the correctly located runtime to capture source delta and fingerprints. Check all protected hashes, exact B11 row IDs, non-B11 matrix preservation and historical defect preservation. Stop private Django processes and the private PostgreSQL cluster after verification. Never commit or push as part of replay.

The evidence describes sampled shared UI checks and explicitly scoped prior assertions. It does not make every business operation, assistive technology or asynchronous combination a newly executed B11 PASS. `check-coverage.json`, `final-journeys.json` and the report retain those limits.
