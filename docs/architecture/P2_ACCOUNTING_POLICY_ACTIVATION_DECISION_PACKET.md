# بسته تصمیم فعال‌سازی سیاست‌های حسابداری

**وضعیت:** تصمیم‌ها در 2026-09-30 ثبت و نسخه‌های نخست منتشر شدند؛ انتخاب/اعمال
Tenant تا تاریخ اثر مجاز نیست.
**دامنه:** فقط `accounting-money-precision` و `accounting-rounding`.

## قاعده تصمیم

هر گزینه‌ای که «منبع بیرونی» دارد، بدون منبع نسخه‌دار و قابل حسابرسی منتشر یا
اعمال نمی‌شود. برای انتخاب Product-defined نیز دلیل کسب‌وکاری/فنی و تاریخ اثر
لازم است. قرارداد فعلی مبنای منبع را در سطح **نسخه سیاست** نگه می‌دارد، نه در
سطح هر فیلد؛ اگر مقادیر یک نسخه مبنای متفاوت داشته باشند، ابتدا باید قرارداد
provenance سطح فیلد جداگانه تصویب و پیاده‌سازی شود.

## تصمیم و اجرای ثبت‌شده

- `accounting-money-precision` v1: `money_scale=0` و
  `intermediate_calculation_scale=6`، همراه با الزام حفظ مقدار میانی بدون
  گردکردن ضمنی.
- `accounting-rounding` v1: `ROUND_HALF_UP`، فقط در مرز
  `final_monetary_line` و با رفتار tie همان `ROUND_HALF_UP`.
- هر دو نسخه **Product-defined** هستند؛ هیچ ادعای قانونی/مقرراتی یا منبع بیرونی
  برای آن‌ها ثبت نشده است.
- تاریخ اثر مشترک `2026-12-22` است: آغاز نزدیک‌ترین دورهٔ باز آیندهٔ Tenant
  مرجع، `demo-construction-01` / «شرکت سازه‌پردازان پارس». آغاز دورهٔ باز جاری
  `2026-09-23` بود و به دلیل منع backdate استفاده نشد.
- Platform Admin نسخه‌ها را با دلیل تصمیم Product Owner منتشر کرده است. هیچ
  انتخاب Tenant وجود ندارد؛ تا رسیدن تاریخ اثر، انتخاب آینده و زمان‌بندی در UI
  مجاز نیست و posting fail-closed می‌ماند.
- UI فقط نسخهٔ منتشرشده، معتبر و مؤثر در تاریخ جاری را قابل انتخاب نشان می‌دهد؛
  نسخه‌های آینده صرفاً به‌صورت اطلاعاتِ فقط‌خواندنی نمایش داده می‌شوند.
- `tenant_policies.approve` منسوخ و غیرفعال است و هیچ مسیر تأیید جداگانه‌ای
  ندارد؛ Tenant Admin با `tenant_policies.apply` انتخاب و اعمال را انجام می‌دهد.

## فرم تصمیم موردنیاز از Product Owner

برای هر دو سیاست، موارد زیر باید صریحاً ثبت شود:

1. مقدار مصوب و گزینه انتخاب‌شده از ردیف‌های 1 تا 5؛
2. مبنای Product-defined یا External-authority برای نسخه؛
3. در حالت External-authority: ناشر، عنوان، شناسه، نسخه، تاریخ انتشار/اثر، دامنه
   کاربرد و دلیل انتساب؛
4. تاریخ اثر آینده و تأیید اینکه هر دو سیاست در آن تاریخ هم‌زمان قابل اعمال‌اند.

تا تکمیل این فرم، schema عملیاتی خالی است، Platform UI انتشار ندارد، Tenant UI
نسخه قابل انتخابی نشان نمی‌دهد و posting حسابداری fail-closed باقی می‌ماند.

## TINF-01 — مسئله مستقل زیرساخت آزمون pytest

**وضعیت:** رفع‌شده برای چرخهٔ دادهٔ مرجع آزمون (2026-10-01).

علت، `flush` در `TransactionTestCase` بود: داده‌های global که فقط با data
migration ایجاد می‌شدند حذف می‌شدند، اما migration دوباره اجرا نمی‌شد. بنابراین
`OrganizationRole` و `BusinessPermission` کانونی از بین می‌رفتند و پس از آن
رگرسیون‌های Accounting نمی‌توانستند سازمان بسازند. همان حالت، `WorkflowType`
ثبت‌شده را نیز حذف می‌کرد و ایجاد سازمان سپس نبودِ قالب سازگاریِ system-owned را
آشکار می‌ساخت.

اکنون `post_migrate`، کاتالوگ authorization را از registry و نقش‌های پیش‌فرض، و
`WorkflowType` را از registry کانونی workflow به‌طور idempotent بازسازی می‌کند.
قالب‌های compatibility فقط در مسیر bootstrap رسمی خودشان و تنها هنگام فقدان از
پیکربندی کد-مالک موجود بازسازی می‌شوند؛ fixture، retry یا seed مخصوص تست افزوده
نشده است. شواهد: دو آزمون واقعی flush، ۶ آزمون Treasury، سه رگرسیون پیشین
Accounting و کل `AccountingFoundationTests` (۲۹ آزمون) همگی سبز شدند.

این شواهد به‌معنای سبز بودن pytest کامل نیست؛ آن اجرا عمداً جزو این رفع محدود
نبود. خطای مستقل registry برای `MATERIAL_DOCUMENTS_LINK` نیز تغییر نکرده و باید
جداگانه رسیدگی شود.
