# مستند مشخصات استک فنی و مسئولیت هر بخش

## 1. هدف سند

این سند، استک فنی پروژه ERP چندمستاجری شرکت‌های پیمانکاری را توضیح می‌دهد و مشخص می‌کند هر بخش از سیستم چه مسئولیتی دارد. هدف اصلی این است که مرز مسئولیت‌ها روشن باشد، توسعه ماژول‌ها قابل کنترل بماند و پروژه در قالب یک معماری Modular Monolith قابل نگهداری پیش برود.

این معماری برای توسعه و بهره‌برداری یک محصول کامل ERP عمرانی تعریف شده است و
دیگر به یک MVP محدود نیست. «محصول کامل» هدف دامنه، کیفیت و آمادگی عملیاتی را
مشخص می‌کند؛ قابلیت‌های پیاده‌سازی‌نشده همچنان باید مطابق `ROADMAP.md`، مرحله‌ای
و پس از تصویب صریح توسعه یابند.

## 2. خلاصه استک مصوب پروژه

| بخش | فناوری | نقش اصلی |
| --- | --- | --- |
| زبان Backend | Python | زبان اصلی پیاده‌سازی منطق سمت سرور |
| فریم‌ورک Backend | Django | مدیریت درخواست‌ها، مدل‌ها، فرم‌ها، احراز هویت، قالب‌ها و منطق وب |
| پایگاه داده | PostgreSQL | ذخیره داده‌های عملیاتی، تراکنشی و گزارش‌پذیر ERP |
| ORM | Django ORM | ارتباط شیءگرا با دیتابیس و کاهش وابستگی مستقیم به SQL خام |
| Frontend | Django Templates | تولید صفحات HTML سمت سرور |
| Styling | Tailwind CSS | طراحی رابط کاربری سریع، منظم و قابل توسعه |
| تعاملات سبک Frontend | HTMX | افزودن رفتارهای پویا بدون نیاز به SPA کامل |
| API آینده | Django REST Framework | ارائه API برای موبایل، اتصال بیرونی یا فرانت‌اند مستقل |
| Jobهای آینده | Celery | اجرای کارهای طولانی یا زمان‌بر در پس‌زمینه |
| Broker/Cache آینده | Redis | صف پیام برای Celery و کش داده‌های پرتکرار |
| معماری | Modular Monolith | توسعه یکپارچه، اما با ماژول‌های جدا و مرزبندی‌شده |
| سبک طراحی داخلی | Lightweight Clean Architecture | جداسازی نسبی منطق کسب‌وکار از View و جزئیات فریم‌ورک |
| تست | pytest و pytest-django | تست منطق، دسترسی‌ها، Queryها و جداسازی مستأجرها |
| کیفیت کد | Ruff | بررسی سریع Style، خطاهای رایج و مرتب‌سازی کد |

## 3. جریان کلی درخواست در سیستم

در حالت معمول، کاربر از مرورگر با سیستم کار می‌کند. درخواست ابتدا به Django می‌رسد، سپس View مناسب اجرا می‌شود، منطق کسب‌وکار از طریق Serviceها انجام می‌شود، داده از PostgreSQL خوانده یا در آن ذخیره می‌شود، و در نهایت خروجی HTML یا پاسخ API به کاربر برمی‌گردد.

```text
Browser
  -> Django URL Routing
  -> View
  -> Form / Permission / Service
  -> Django ORM
  -> PostgreSQL
  -> Template / HTMX Partial / API Response
  -> Browser
```

اگر درخواست از نوع HTMX باشد، معمولاً فقط یک قطعه HTML کوچک برمی‌گردد؛ برای مثال ردیف‌های جدول، محتوای Modal یا نتیجه فیلتر.

## 4. مسئولیت هر لایه در استک

### 4.1 مرورگر کاربر

مرورگر محل نمایش رابط کاربری و دریافت تعاملات کاربر است.

مسئولیت‌ها:

- نمایش صفحات HTML
- ارسال فرم‌ها
- اجرای CSS و مقدار کمی JavaScript
- اجرای درخواست‌های HTMX برای تعاملات سبک
- نمایش خطاها، پیام‌ها، جدول‌ها، فرم‌ها و داشبوردها

مرورگر نباید مسئول اجرای منطق اصلی کسب‌وکار باشد. برای مثال محاسبه نهایی وضعیت قرارداد، کنترل دسترسی یا تشخیص Tenant معتبر باید در سمت سرور انجام شود.

### 4.2 Django Templates

Django Templates مسئول تولید HTML سمت سرور است. در این پروژه، چون رابط کاربری ERP معمولاً فرم‌محور و داده‌محور است، Templateها انتخاب مناسبی هستند.

مسئولیت‌ها:

- تولید صفحات HTML
- نمایش داده‌های آماده‌شده توسط View
- نمایش فرم‌ها، جدول‌ها، فیلترها و جزئیات رکوردها
- استفاده از Componentهای تکرارشونده مثل Header، Sidebar، جدول و پیام‌ها
- نمایش Partial Template برای HTMX

Template نباید محل تصمیم‌های اصلی کسب‌وکار باشد. شرط‌های ساده نمایشی قابل قبول هستند، اما منطق‌هایی مثل محاسبه مبلغ قرارداد یا کنترل دسترسی باید بیرون از Template باشد.

### 4.3 Tailwind CSS

Tailwind CSS مسئول ظاهر رابط کاربری است. این ابزار کمک می‌کند بدون ساخت فایل‌های CSS بزرگ و پراکنده، طراحی منظم و سریع پیاده‌سازی شود.

مسئولیت‌ها:

- طراحی Layout صفحات
- کنترل فاصله‌ها، رنگ‌ها، اندازه‌ها و Typography
- ساخت ظاهر فرم‌ها، دکمه‌ها، جدول‌ها، کارت‌ها و منوها
- ایجاد Design System سبک برای صفحات ERP

پیشنهاد می‌شود کلاس‌های پرکاربرد در Componentهای Template یا فایل‌های مشترک نگهداری شوند تا ظاهر سیستم یکدست بماند.

### 4.4 HTMX

HTMX برای اضافه کردن تعاملات پویا به صفحات Django استفاده می‌شود، بدون اینکه کل Frontend به React یا Vue تبدیل شود.

مسئولیت‌ها:

- ارسال درخواست‌های جزئی به سرور
- جایگزینی بخشی از صفحه با HTML برگشتی
- فیلتر، جست‌وجو و صفحه‌بندی بدون Reload کامل صفحه
- باز کردن فرم‌ها در Modal
- ثبت یا حذف ردیف‌های جزئی در فرم‌های پیچیده
- ساخت تجربه کاربری سریع‌تر در صفحات ERP

نمونه کاربردهای مناسب:

- فیلتر جدول پروژه‌ها
- جست‌وجوی طرف قرارداد
- انتخاب وابسته پروژه و قرارداد
- افزودن ردیف به صورت‌وضعیت
- نمایش فرم ویرایش در Modal

HTMX نباید جایگزین معماری Backend شود. منطق اصلی همچنان باید در Form، Service، Selector و Permission باقی بماند.

### 4.5 Django URL Routing

URL Routing مسئول اتصال مسیرهای وب به Viewهای مناسب است.

مسئولیت‌ها:

- تعریف آدرس صفحات و عملیات
- تفکیک URLهای هر ماژول
- هدایت درخواست‌ها به View درست
- خوانا نگه داشتن ساختار مسیرهای سیستم

نمونه مسیرها:

```text
/projects/
/projects/create/
/projects/<id>/edit/
/contracts/
/statements/
/reports/
```

### 4.6 Django Views

View هماهنگ‌کننده درخواست و پاسخ است. View باید ورودی را بگیرد، دسترسی را بررسی کند، Form یا Service مناسب را صدا بزند و پاسخ مناسب برگرداند.

مسئولیت‌ها:

- دریافت Request
- تشخیص Tenant فعال
- بررسی Login و Permission
- فراخوانی Form برای اعتبارسنجی ورودی
- فراخوانی Service برای عملیات تغییردهنده
- فراخوانی Selector برای خواندن داده
- انتخاب Template مناسب
- برگرداندن HTML، Partial HTML یا Response مناسب

View نباید پر از منطق کسب‌وکار شود. اگر View طولانی شد، معمولاً نشانه این است که باید بخشی از منطق به Service یا Selector منتقل شود.

### 4.7 Forms

Form مسئول اعتبارسنجی داده‌های ورودی کاربر در رابط وب است.

مسئولیت‌ها:

- بررسی الزامی بودن فیلدها
- کنترل نوع داده
- اعتبارسنجی اولیه ورودی‌ها
- آماده‌سازی داده تمیزشده برای Service
- نمایش خطاهای قابل فهم به کاربر

Form می‌تواند اعتبارسنجی‌های مرتبط با ورودی داشته باشد، اما عملیات اصلی مثل ایجاد قرارداد، ثبت سند یا تغییر وضعیت پروژه بهتر است در Service انجام شود.

### 4.8 Services

Service محل اجرای Use Caseها و منطق تغییردهنده سیستم است. در ERP، این لایه بسیار مهم است چون قوانین کسب‌وکار نباید در Viewها پخش شوند.

مسئولیت‌ها:

- ایجاد، ویرایش و حذف رکوردها
- اجرای قوانین کسب‌وکار
- کنترل تراکنش‌های مهم
- شماره‌گذاری اسناد
- ثبت Audit Log
- اعمال محدودیت‌های Tenant
- اجرای عملیات چندمرحله‌ای
- جلوگیری از تکرار منطق در چند View یا API

نمونه عملیات مناسب برای Service:

```text
create_project
update_contract_status
submit_statement
approve_statement
attach_document_to_contract
```

### 4.9 Selectors

Selector محل Queryهای خواندنی و گزارش‌گیری است. این بخش کمک می‌کند Viewها تمیز بمانند و Queryهای پیچیده در یک جای مشخص نگهداری شوند.

مسئولیت‌ها:

- خواندن لیست رکوردها
- فیلتر براساس Tenant
- فیلتر براساس وضعیت، تاریخ، پروژه یا شرکت
- آماده‌سازی داده برای جدول‌ها و گزارش‌ها
- بهینه‌سازی Queryهای پرتکرار

نمونه عملیات مناسب برای Selector:

```text
get_project_list_for_tenant
get_contract_detail
get_active_projects
get_statement_report_rows
```

### 4.10 Models

Model مسئول تعریف ساختار داده و قواعد ذاتی موجودیت‌هاست. Django ORM از Modelها برای ساخت و مدیریت جداول دیتابیس استفاده می‌کند.

مسئولیت‌ها:

- تعریف Entityها
- تعریف فیلدها و نوع داده‌ها
- تعریف ارتباط بین مدل‌ها
- تعریف Constraintها و Indexها
- نگهداری قواعد ذاتی و ساده مدل

در سیستم چندمستاجری، بیشتر مدل‌های تجاری باید به Tenant متصل باشند.

نمونه:

```python
class Project(models.Model):
    organization = models.ForeignKey(
        "organizations.Organization",
        on_delete=models.PROTECT,
    )
    code = models.CharField(max_length=50)
    title = models.CharField(max_length=255)

    class Meta:
        constraints = [
            models.UniqueConstraint(
                fields=["organization", "code"],
                name="uq_project_organization_code",
            )
        ]
```

### 4.11 Django ORM

Django ORM واسط بین کد Python و PostgreSQL است. به جای نوشتن SQL مستقیم در اکثر موارد، با Modelها و QuerySetها کار می‌شود.

مسئولیت‌ها:

- تبدیل Modelها به جدول
- اجرای Queryها
- مدیریت ارتباط بین موجودیت‌ها
- کمک به Migrationها
- اجرای فیلترها، Aggregateها و Annotationها
- کاهش وابستگی مستقیم کد به SQL خام

در بخش‌های حساس یا گزارش‌های سنگین، استفاده کنترل‌شده از SQL خام یا Viewهای دیتابیس قابل قبول است؛ اما منطق عمومی بهتر است با ORM پیاده‌سازی شود.

### 4.12 PostgreSQL

PostgreSQL 18.6 با Psycopg 3 مبنای فعلی و مرجع پایگاه دادهٔ محصول است و تمام
محیط‌ها باید migrationهای جنگو را روی همین بستر اعمال کنند.

مسئولیت‌ها:

- ذخیره داده‌های عملیاتی ERP
- اجرای تراکنش‌ها
- حفظ Constraintها
- مدیریت Indexها
- پشتیبانی از Queryهای تحلیلی و گزارشی
- حفظ سازگاری داده‌ها
- پشتیبانی از Backup و Restore

برای سیستم ERP، دیتابیس فقط محل ذخیره ساده نیست؛ بخش مهمی از صحت داده‌ها با Constraint، Transaction و Index درست تضمین می‌شود.

### 4.13 Django REST Framework

DRF لایه API آینده سیستم است. تا زمانی که نیاز جدی به API وجود ندارد، لازم نیست تمام پروژه از ابتدا API محور شود.

مسئولیت‌ها:

- ارائه API برای موبایل
- اتصال به سامانه‌های بیرونی
- ارائه Endpoint برای گزارش‌ها یا سرویس‌های جانبی
- سریال‌سازی داده‌ها
- اعتبارسنجی ورودی API
- کنترل Permission در سطح API

نکته مهم این است که DRF نباید منطق جداگانه‌ای از Viewهای وب داشته باشد. API View باید همان Serviceها و Selectorهایی را صدا بزند که Viewهای معمولی استفاده می‌کنند.

### 4.14 Celery

Celery برای اجرای کارهای زمان‌بر یا سنگین در پس‌زمینه استفاده می‌شود. این بخش در نسخه‌های بعدی می‌تواند به پروژه اضافه شود.

مسئولیت‌ها:

- تولید گزارش‌های سنگین
- Import فایل Excel
- ارسال ایمیل یا پیامک
- پردازش اسناد
- تولید PDFهای حجیم
- اجرای Jobهای زمان‌بندی‌شده
- اتصال دوره‌ای به سامانه‌های بیرونی

کارهای Celery در سیستم چندمستاجری باید Tenant را صریح دریافت کنند و قبل از اجرا اعتبارسنجی شوند.

### 4.15 Redis

Redis معمولاً در این استک دو نقش اصلی دارد: صف پیام برای Celery و کش داده‌های پرتکرار.

مسئولیت‌ها:

- نگهداری صف Jobهای Celery
- ذخیره موقت داده‌های پرتکرار
- کمک به کاهش فشار روی دیتابیس
- نگهداری موقت وضعیت برخی عملیات‌ها

در سیستم چندمستاجری، کلیدهای Redis باید Tenant-aware باشند؛ یعنی شناسه Tenant در کلید لحاظ شود تا داده‌ها با هم مخلوط نشوند.

نمونه:

```text
tenant:42:dashboard:summary
tenant:42:project:list
```

## 5. معماری Modular Monolith

در این پروژه، سیستم به شکل یک برنامه واحد توسعه و استقرار داده می‌شود، اما داخل آن به ماژول‌های مستقل تقسیم می‌شود.

مسئولیت این سبک معماری:

- ساده نگه داشتن توسعه و استقرار
- جلوگیری از پیچیدگی Microservices
- تفکیک منطقی بخش‌های کسب‌وکار
- امکان رشد تدریجی سیستم
- کنترل هزینه و پیچیدگی نگهداری در چرخهٔ عمر یک محصول کامل

نمونه ماژول‌ها:

```text
apps/
  accounts/
  organizations/
  parties/
  materials/
  projects/
  contracts/
  workforce/
  procurement/
  inventory/
  equipment/
  daily_reports/
  documents/
  financials/
  audit/
```

هر ماژول بهتر است مسئولیت مشخصی داشته باشد و تا حد ممکن منطق داخلی خود را نگه دارد.

## 6. سبک Lightweight Clean Architecture

منظور از Clean Architecture سبک در این پروژه، جداسازی مسئولیت‌ها بدون افراط در Interface، Repository و لایه‌های زیاد است.

ساختار پیشنهادی هر ماژول:

```text
projects/
  models.py
  forms.py
  views.py
  services.py
  selectors.py
  permissions.py
  urls.py
  tests/
```

مسئولیت فایل‌ها:

| فایل | مسئولیت |
| --- | --- |
| `models.py` | تعریف داده و ارتباط‌ها |
| `forms.py` | اعتبارسنجی ورودی صفحات وب |
| `views.py` | هماهنگی درخواست، پاسخ و Template |
| `services.py` | عملیات تغییردهنده و منطق کسب‌وکار |
| `selectors.py` | Queryهای خواندنی و گزارش‌گیری |
| `permissions.py` | کنترل دسترسی‌های ماژول |
| `urls.py` | مسیرهای ماژول |
| `tests/` | تست رفتار، امنیت و Tenant Isolation |

## 7. چندمستاجری در استک

در ERP چندمستاجری، چند شرکت یا مشتری از یک نرم‌افزار استفاده می‌کنند، اما داده‌های هرکدام باید جدا بماند.

مدل پیشنهادی:

```text
یک برنامه Django
یک دیتابیس PostgreSQL
یک Schema اصلی
ستون tenant_id در جداول تجاری
```

مسئولیت‌های مهم چندمستاجری:

- تشخیص Tenant فعال از کاربر، Session، Subdomain یا Context درخواست
- جلوگیری از اعتماد به `tenant_id` ارسال‌شده توسط کاربر
- فیلتر تمام Queryها براساس Tenant
- افزودن Tenant به Unique Constraintها
- جداسازی فایل‌ها، کش و گزارش‌ها براساس Tenant
- تست عدم نشت داده بین Tenantها
- تفکیک مدیر سامانه از مدیر مستأجر

## 8. احراز هویت و دسترسی

احراز هویت مشخص می‌کند کاربر کیست. سطح دسترسی مشخص می‌کند کاربر اجازه چه کاری دارد.

مسئولیت‌ها:

- ورود و خروج کاربران
- مدیریت کاربران هر Tenant
- تعریف نقش‌ها
- کنترل دسترسی به صفحات
- کنترل دسترسی به رکوردها
- جلوگیری از دسترسی مستقیم از طریق URL

در ERP، فقط مخفی کردن دکمه‌ها کافی نیست. هر عملیات سمت سرور نیز باید Permission را بررسی کند.

## 9. تست و کنترل کیفیت

### pytest و pytest-django

مسئولیت‌ها:

- تست Serviceها
- تست Queryها و Selectorها
- تست Viewها
- تست فرم‌ها
- تست Permissionها
- تست جداسازی Tenantها
- تست عملیات حساس مالی یا قراردادی

مهم‌ترین تست‌ها برای این پروژه:

```text
کاربر Tenant A نباید رکورد Tenant B را ببیند.
کاربر Tenant A نباید رکورد Tenant B را ویرایش کند.
کاربر Tenant A نباید در گزارش‌ها داده Tenant B را دریافت کند.
کاربر Tenant A نباید با تغییر URL به رکورد Tenant B دسترسی پیدا کند.
```

### Ruff

Ruff مسئول کنترل کیفیت کد Python است.

مسئولیت‌ها:

- پیدا کردن خطاهای رایج
- کنترل Style کد
- مرتب‌سازی Importها
- کمک به یکدست ماندن کد
- اجرای سریع در محیط توسعه و CI

## 10. استقرار پیشنهادی

برای استقرار، اجزای زیر معمولاً استفاده می‌شوند:

| بخش | مسئولیت |
| --- | --- |
| Gunicorn یا uWSGI | اجرای برنامه Django |
| Nginx | Reverse Proxy، مدیریت Static File و HTTPS |
| PostgreSQL Server | اجرای دیتابیس |
| Redis | صف Jobها و کش |
| Celery Worker | اجرای کارهای پس‌زمینه |
| Celery Beat | اجرای Jobهای زمان‌بندی‌شده |
| Docker Compose | ساده‌سازی اجرای سرویس‌ها |

استقرار پایه می‌تواند با اجزای ضروری آغاز شود و Celery/Redis فقط هنگام ایجاد
نیاز عملیاتی واقعی اضافه شود؛ این تصمیم معماری به معنی محدود کردن محصول به MVP
نیست و الزامات امنیت، پشتیبان‌گیری، بازیابی و پایش را کاهش نمی‌دهد.

## 12. اصل راهنما برای ادامه پروژه

برای ادامه توسعه این ERP، بهتر است منطق اصلی کسب‌وکار در Serviceها، Queryهای خواندنی در Selectorها، اعتبارسنجی ورودی در Formها و هماهنگی درخواست‌ها در Viewها قرار بگیرد. PostgreSQL مسئول نگهداری قابل اعتماد داده‌هاست و Template، Tailwind و HTMX تجربه کاربری را بدون پیچیده کردن Frontend تأمین می‌کنند.

این ترکیب برای چرخهٔ عمر یک محصول کامل ERP چندمستاجری، انتخابی عملی، قابل
استقرار و قابل توسعه است و اجازه می‌دهد دامنه‌های جدید بدون شکستن مرزهای امنیتی
و معماری به‌صورت مرحله‌ای افزوده شوند.
