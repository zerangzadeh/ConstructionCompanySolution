## Recommended exact control contract

1. **Dependency sets.** Runtime direct requirements are `requirements.txt` plus `requirements-db.txt`: Django, python-dotenv and `psycopg[binary]`, with their exact resolved transitives in a Linux production hash lock. Development/test adds `requirements-dev.txt` (pytest-django and Ruff) in a separate Linux development hash lock; those tools must not enter the production environment. Build/deployment has the pinned Python base image and pip as acquisition tooling only; no application package or process manager is added by this decision. SCA/SBOM tooling is isolated from runtime, explicitly inventoried and pinned before CI use. Any new application dependency or version change requires its own documented security/license/compatibility review under CEP-013's existing boundary. `RMB-0601` must be re-evaluated against the exact selected lock; the older sqlparse finding does not prove current clearance.
2. **Acquisition source.** Approve direct HTTPS PyPI (`https://pypi.org/simple/` with PyPI's authenticated artifact host) **for controlled build/CI acquisition only**. No `--extra-index-url`, alternate index, plain HTTP or `--trusted-host`. Production deployment installs only from an attested, immutable artifact/wheelhouse produced by that build and must not resolve from the internet. If private connectivity requires a mirror later, its exact hostname, TLS trust root, upstream synchronization and operator must be separately approved before switching; a mirror is not silently equivalent to PyPI.
3. **Integrity and provenance.** Pin every direct and transitive package version and selected distribution SHA-256; enforce `pip --require-hashes` with no source-build or unpinned fallback. Pin the base image by full immutable digest and record Python, pip, OS, architecture, index identity, source project/version, artifact filename/hash, acquisition timestamp, build revision and lock/SBOM hashes. Preserve available upstream attestations as evidence, without treating their absence as proof of authenticity. Missing hash, artifact, TLS validation, source identity or provenance record **fails closed**, creates a finding and blocks release readiness; the maintainer may submit a reviewed lock/source update, never silently fetch an alternative. Hash mode is supported by [pip's secure-install guidance](https://pip.pypa.io/en/stable/topics/secure-installs/).
4. **Vulnerabilities.** Security and Privacy Reviewer owns triage/disposition; Authorized Technical Maintainer prepares updates and evidence; independent Release Certification Owner checks gate completeness. Every scanner/advisory result is linked to the exact package/version, lock, artifact, source and candidate. Unknown/unscanned findings block. Critical/High security exposure blocks and cannot be waived; an exploitable dependency needs an effective approved fix or containment and rerun. Medium/Low may proceed only with evidence-backed impact, compensating controls, remediation owner/date, expiry no later than the next release or 90 days, and Product Owner + Certification Owner + Security/Privacy Reviewer approval, as in P10 section 9.4. Otherwise the gate fails. No automatic scanner-severity downgrade or implicit exception.
5. **Licenses.** The Security and Privacy Reviewer owns inventory completeness and technical provenance; the Product Owner, with legal review where required, owns commercial compatibility/acceptance. **Allow** only an exact package/version/artifact with a recorded license text/identifier and approved compatibility disposition for BONIRA SaaS distribution/use. **Review** every new, changed, dual or ambiguous license before release. **Block** unknown license, missing license evidence, or an expressly rejected/incompatible obligation. A proposed exception records exact artifact, license terms, usage/distribution impact, counsel/Product Owner decision, compensating action, owner and expiry; no automatic allowlist or silent exception is inferred. Security cannot waive an unreviewed legal obligation.
6. **Evidence and scope.** CI must fail on unavailable scanner/index, unreviewed findings, hash/lock drift or incomplete SBOM/license/provenance output and retain a failure/exception artifact without secrets. Evidence includes exact candidate/environment identity and cannot promote production/runtime readiness without later environment-specific verification. This is repository/CI supply-chain control; it grants no Tenant business permission and changes no runtime Tenant data path. Required CEP permission/tenant-isolation assertions should verify that the new technical gate introduces no application access surface or authorization bypass, with applicability recorded rather than invented Tenant behavior.
