## Existing and prepared signals

`core.telemetry` remains the technical HTTP source: server correlation UUID,
registered route, method, status and handler duration. Body, query, raw path,
headers, exception text, tenant and actor identifiers are excluded. It is not the
append-only business audit or any financial authority. Duration excludes streaming
delivery. Loss of primary/fallback logging never establishes durable delivery.

`python manage.py operational_health --settings=<explicit-approved-settings>`
probes the configured PostgreSQL connection using a read-only SELECT 1 and the
configured cache using a fresh namespaced GET. Both probes run even if one fails.
Only sanitized reachable/unreachable signals are printed; any failed dependency
returns a nonzero command result. No endpoint, membership bypass, cache write,
domain read, schema mutation or business operation is introduced. This command
uses process-level operator credentials; restrict those through the selected
operating environment. A reachable local/dummy cache alone does not prove a
shared cache or password-recovery correctness.

| Signal | Source / local rule |
| --- | --- |
| database.reachable / database.unreachable | Read-only dependency probe; failure is an alert event |
| cache.reachable / cache.unreachable | Cache GET probe; failure is an alert event |
| http.server_error | Existing http.response with an integer HTTP 500..599; discrete event, no invented error-rate threshold |
| telemetry.delivery_failed | Existing fallback event; local alert event |

`core.operations.request_failure_signal` projects only the registered technical
events. `LocalOperationsAdapter` is a disposable local file destination for alert
delivery/retention tests; it accepts no external destination or arbitrary payload.
No network alert is sent. It records explicit NOT_VALIDATED Production status.
Delivery errors propagate to its caller for failure evidence. No deployment
logging handler, scheduled job or external integration has been activated.

The adapter implements retention planning by explicit aware cutoff; execution is
opt-in and confined to files generated by that adapter in its own temporary root.
No default duration, business/audit deletion or production storage path exists.
Its temporary directory is removed on context exit. Production retention periods,
holds, archive/disposal and sink lifecycle require approved input; test cleanup
does not approve a production retention rule.

Financial/integration domain signals need their registered producer and failure
meaning approved before instrumentation. An HTTP status is not a failed posting,
settlement, reconciliation or inventory fact. The technical catalogue above is
already implemented and must not be requested as an unresolved basic choice.

## Runbook OP-01: signal or delivery failure

Retain incident identity, environment/artifact/config identity, UTC timestamps,
sanitized signal and correlation ID. Confirm destination receipt; missing receipt
is failure/UTV, not an acknowledgement. A designated Incident Owner records impact
assessment, bounded actions and evidence references. If the local pipeline fails,
retain sanitized operator diagnostics independently; don't replay a business
action to force telemetry. The named escalation path must supply contacts and
authority before activation. No response deadline/MTTR is inferred.

## Runbook OP-02: dependency failure / deployment recovery

Record both dependency results and explicit NOT_VALIDATED readiness. Inspect
approved service/TLS configuration without dumping credentials. Coordinate with
the release/rollback owner using the [deployment procedure](CEP-071_DEPLOYMENT_PREPARATION.md).
Never write a journal, repair business data or alter tenant permissions as a
health-check workaround. Recovery and revalidation require target-specific
evidence and a recorded acceptance decision.

## Runbook OP-03: support access, expiry and revocation

Use only `apps.support.services.request_access`, `confirm_access`,
`validate_access` and `revoke_access` through existing authorized routes/services.
Membership/tenant status, registered business permission, tenant/object scope,
purpose/scope and expiry remain enforced inside existing transactions. The
requester cannot self-approve; tenant and independent platform confirmations are
required. Every use revalidates the grant. Expired grants fail closed without a
cleanup job; revocation is idempotent, audited and makes later use fail closed.
No raw model update, shell-created grant, superuser bypass or emergency role is
authorized. The operating policy must designate who holds the existing required
authority; being named in a runbook grants no permission.

Record request/grant references, permitted purpose/scope/expiry, the authorized
revoking actor and audit evidence in the restricted incident record. Do not copy
personal identifiers into technical logs. Existing focused support tests cover
independence, expiry, revocation, purpose/scope and audit behavior.
