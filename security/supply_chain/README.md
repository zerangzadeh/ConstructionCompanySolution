# CEP-013 supply-chain operating contract

The Human-approved target and policy are in [`CEP-013_SUPPLY_CHAIN_DECISION.md`](../../CEP-013_SUPPLY_CHAIN_DECISION.md). This directory records **Development build controls**, not production certification or permission to change application package versions.

## Acquisition and evidence

`requirements-prod-linux.lock` contains the runtime set; `requirements-dev-linux.lock` adds test/lint tools. Both are exact version and selected Linux-wheel hash locks for CPython 3.11.17, Debian 12, `linux/amd64`. The historical Windows `requirements-lock.txt` remains separate. The official Python base-image tag and pinned index/platform digests are in `build_image.json`; a tag/digest mismatch blocks the gate. The build uses only HTTPS PyPI; deployment must consume the attested wheelhouse offline.

Run `python scripts/supply_chain.py check-locks` for a fast local check. Run `python scripts/supply_chain.py gate --wheelhouse <disposable-dir> --output <evidence-dir>` for hash-checked online acquisition, offline resolution, image-identity check, OSV advisory query, CycloneDX SBOM and license inventory. The command exits nonzero for missing/unreviewed evidence and always writes `gate-result.json`. Its output is evidence for the exact timestamp, lock, platform and source only; `BUILD_CONTROL_PASS` does not mean production/runtime PASS. CI additionally performs an offline `pip install --require-hashes` inside the pinned Linux build image, then runs focused tests, Ruff, Django checks and a signed wheelhouse attestation. A later deploy gate must verify that attestation against the expected repository/workflow/commit and archive digest before installation. If GitHub artifact attestation is unavailable for the repository plan, release remains blocked; do not skip the step.

The build report and wheelhouse must be retained under restricted release evidence with the candidate ID, source revision, image digest, lock/SBOM/archive hashes, timestamp, signer identity, findings and exception decisions. The CI evidence artifact contains no application secrets or Tenant data. No production release is authorized here.

## Disposition and changes

- Security and Privacy Reviewer owns advisory triage and license evidence completeness. Critical/High or unknown severity blocks; only Medium/Low may have an exact-lock, time-limited exception with Product Owner, independent Certification Owner and Security/Privacy Reviewer approval. `vulnerability_exceptions.json` is empty by default. Never edit an exception solely to make CI green.
- Product Owner, with legal review where required, owns exact artifact license acceptance. `license_approvals.json` records the 15 exact approved Linux wheels; the rejected `psycopg-binary` wheel is absent. Each `ALLOW` entry must match `name==version:artifact_sha256` and the exact wheel license text hash, and record a reviewed license expression, Product Owner, date and compatibility reason. The expression must equal wheel metadata when declared; when metadata has no expression, the reviewer must add `license_source_evidence`. Unknown, changed, missing or rejected terms block. The pure Psycopg artifact retains its recorded conditional disposition; the binary artifact remains rejected outside the approved Linux sets.
- Dependabot proposes dependency and action updates weekly; it does not merge. The Authorized Technical Maintainer records the purpose, support/advisory/license review and compatibility impact; the Security and Privacy Reviewer and Product Owner approve package changes as required. Regenerate both Linux locks only from the approved direct sets and selected Linux wheels, pin every new hash, rerun acquisition/scan/tests and record source/version/artifact provenance. A lock update or image update invalidates affected prior evidence. No application package addition, removal or version change is authorized merely because a PR exists.
- If PyPI, the image registry, advisory service, signing service, artifact or hash is unavailable, the gate blocks and retains a failure record. Do not use a different index, source distribution, trusted-host override, unpinned fallback or inferred license waiver.

No application routes, services, Tenant data or permission grants are introduced by this control; Tenant business authorization remains governed by existing application services. Review of actual CI attestation and production install is a later environment-specific gate.
